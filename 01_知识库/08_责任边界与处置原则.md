# 08 责任边界与处置原则

> 归因的终点不是"是什么原因"，而是"**该找谁、做什么**"。本文件定义责任边界与处置原则。

---

## 一、责任方一览

| 责任方 | 负责范围 | 典型动作 |
|---|---|---|
| **获客运营** | 预算、基础出价、投放开关 | 调预算、调出价、暂停/恢复投放 |
| **获客策略** | RTA 排除、W×Q 系数表、排除包、回传口径 | 改系数、改排除规则、改回传配置 |
| **获客模型** | preA/preG 模型、额度子分 | 模型版本迭代、特征调整 |
| **渠道对接人** | 与媒体的沟通 | 向媒体发起定向/流量核查 |
| **风险** | A 卡 / G 卡审批口径、资产评级 | 审批阈值调整 |
| **资金** | 资金路由、资方额度 | 路由排查、资方协调 |
| **产品** | 申请流程、页面、预授信提示 | 流程优化、页面修复 |
| **数据 / 研发** | 回传链路、埋点、放款技术链路 | 链路排查、数据修复 |
| **素材** | 素材供给 | 新素材上线、老素材下线 |

> 【源资料未确认】真实业务中执行链路上还有**代理**这一环。本模拟环境不包含代理。

## 二、症状 → 责任方的映射

| 症状 | 第一责任方 | 说明 |
|---|---|---|
| 计费比偏高 | **获客运营 / 策略先核验**；必要时联动渠道对接人 | 先拆花费、转化数与实际 Bid，不能仅凭计费比认定媒体责任 |
| 计划预算撞线 / 消耗不足 | **获客运营** | 预算与出价 |
| 首登成本上升 | 运营 + 数据/研发（承接链路） | 需先分"流量质量"还是"承接链路" |
| 首登→申完下降 | **产品** | 申请流程、页面体验 |
| 申完→授信下降 | **风险** | A 卡审批口径 |
| 安全过件率下降（安全授信数 ÷ 申完数） | **策略 / 模型 / 风险先联合核查** | 安全授信户为授信环节 A 卡前 3 组；检查客群、审批与 A 卡分组分布，再结合腾讯计费比等线索判断是否联动媒体 |
| 平均额度下降 | **风险 / 额度策略** | 额度模型或额度规则 |
| 动支率下降、发起量也下降 | **风险 / 产品** | 意愿或额度预期问题 |
| **动支率下降、发起量正常** | **资金 / 研发先核查**，必要时联动风险 | 优先查执行链路，同时检查发起后审批、资金策略与数据口径 |
| 应回传对象的发送成功率下降 | **数据 / 研发** | 核对成功数、应回传数与接口日志 |
| 符合回传规则的覆盖率下降 | **获客策略**，必要时联动风险 | 核对额度档、模型分箱、时效与规则命中量；本环境无覆盖率明细，不能由“回传比例”直接判定 |
| 消耗跑不出去（素材 CTR 衰退） | **素材 + 运营** | 换素材 |
| 消耗跑不出去（回传/pCVR 问题） | **数据 / 策略** | 回传链路或配置 |
| 局部子组严重劣化 | **策略 / 运营** | 定位到具体子组 |
| 全渠道同时同幅异动 | **数据** | 优先怀疑数据问题 |

## 三、处置原则（六条）

### 原则一：先止血，再定位

当损失在持续发生时（如 CPS 高速上涨、成功率腰斩），**先执行可逆的止血动作（降量/暂停），再定位根因**。

> 但**降量本身有代价**（规模损失、可能错过窗口），因此止血动作必须带**回滚条件**。

### 原则二：区分"暂时无解"与"有解"

| 情况 | 处置 |
|---|---|
| 可定位到具体环节 | 立即给出具体动作 |
| 只能定位到方向（两个候选不可区分） | **给出证伪路径**——指明补哪一项数据就能收敛，并给出"若 A 则…若 B 则…"的双分支动作 |
| 完全无解 | 明确说明，并给出临时观测方案 |

> ⭐ **不要为了给答案而强行选一个。** 运营按错误归因执行的真实代价（找错责任方、错过干预窗口、在坏数据上降量）远高于"暂时不知道"。

### 原则三：区分"异常"与"预期内变化"

| 类型 | 处置 |
|---|---|
| 非预期变化 | 作为异常处置 |
| **我方主动收紧风控 / 主动改造导致的变化** | **属策略意图，不应作为异常处置**；应登记为"预期变化"并抑制对应告警 |

> ⚠️ **并非所有指标下降都是异常。** 很多告警产品的失效就源于把"策略意图"误报为"业务异常"。

### 原则四：动作必须可执行到粒度

| ❌ 不可执行 | ✅ 可执行 |
|---|---|
| "加强监控" | "将该账户日预算从 8 万下调至 2 万，4 小时后若 CPS 回落至 0.48 以下则逐步恢复" |
| "排查质量问题" | "拉取该账号过去 7 天的 RTA 参竞率、排除包命中率、preA/preG 分档分布" |
| "关注消耗" | "今日内上线 2 条新素材，优先替换 CTR 最低的素材 A" |

### 原则五：量化影响与代价

把技术指标翻译成业务语言：

| 技术表述 | 业务表述 |
|---|---|
| 动支率腰斩 | 当日首借金额减少约 XX 万元 |
| 消耗进度落后 23pp | 全天预计少消耗 XX 万元，按当前 CPS 折算首借金额少 XX 万元 |
| CPS 上升 15% | 达到同样资产规模需多花 XX 万元 |

> **运营对"成功率腰斩"没有直觉，对"今天少放 38 万"有直觉。**

### 原则六：每一次都修补机制

| 机制缺口类型 | 修补方向 |
|---|---|
| 检测不到（慢变量、局部劣化） | 加趋势巡检、加结构体检 |
| 看不到（过程指标无独立告警） | 让过程指标可独立触发 |
| 判据缺失（某渠道无内外分水岭） | 补替代判据 |
| 阈值失准（跨渠道） | 改动态基线 |
| 拦截不了（数据合法但错误） | 加合理性前置校验 |
| 归因错误（规则树误判） | 修正归因规则 |
| 无闭环（建议无人承接） | 建"异动 → 动作 → 效果"台账 |

---

## 四、⚠️ 处置前必须检查的三件事

| # | 检查 | 不检查的后果 |
|---|---|---|
| 1 | **数据是否可信** | 在坏数据上做动作 = 真实损失 |
| 2 | **对照组是否干净** | 实验结论被外部冲击污染 |
| 3 | **同期是否还有其他变更** | 把多个变更的效果归给其中一个 |

---

## 五、绝对不要做的事

| # | 禁止 | 原因 |
|---|---|---|
| 1 | 在小样本上做动作 | 噪音驱动，动作无效且消耗信任 |
| 2 | 只为 CPS 省钱而牺牲质量 | 质量塌陷会在 1–4 周后反噬成本与资产质量 |
| 3 | 只看大盘不看结构 | 局部问题可能被平均掩盖（严重程度可达大盘的数倍） |
| 4 | 混用时间窗 | T0 / T3 / T7 / 实际 / M0 结论不可比 |
| 5 | 把相关性当因果 | 时间吻合不等于因果，需排除同期变更 |
| 6 | 给出无法执行的建议 | 建议的可行性是产品价值的一部分 |
| 7 | 在报告里断言超出数据支持范围的结论 | 错误归因的代价远高于"暂时不知道" |

## 六、升级与追踪的一般框架

| 时点 | 观测内容 | 升级条件 |
|---|---|---|
| 30 分钟 / 即时 | 核心指标是否继续恶化 | 恶化 → 提升告警级别，同步更高级别责任方 |
| 2 小时 | 处置动作是否生效 | 未生效 → 判定动作无效，转其他分支 |
| 次日 | 全天指标 + 排查结论是否回填 | 结论未回填 → 提醒责任方 |
| T+3 / T+7 | 中期效果 | 未恢复 → 升级为专题复盘 |
| 连续 3 个窗口未恢复 | 自动升级 | 建议启动跨部门联合复盘 |
| 效果回收 | 记录"异动 → 动作 → 结果" | 写入台账，沉淀为可复用的经验系数 |
