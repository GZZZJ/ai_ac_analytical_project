### 验证

```bash
.venv/bin/python -m unittest discover -s tests -v
cd frontend && npm run build
```

测试覆盖四类 Analyzer、CPS 两因素绝对贡献对账、校验阻断、多问题局部澄清、追问、实际日期缺数与协作式停止。单问题分析仍由 LangGraph 执行；新增的本地交接层保存 TaskSpec、DataNeed、DataResult、Finding、VerificationResult、ReportSpec 与步骤依赖计划。语义查询把只读 CSV 映射到临时 SQLite 表，通过内部生成的参数化 SELECT 查询，并在 DataResult 记录 SQL、范围、行数、跨表对账与覆盖检查。结果校验从原始模拟数据复算四类问题的关键数字；报告摘要只使用已校验的结论，并做最终版本一致性检查。多个问题可用分号或换行分隔，父请求记录各分项状态，最多三个分项并发执行；待澄清的分项可单独继续，运行中和待澄清的分项可单独取消。修改一个分项的范围会生成新任务版本并保留旧结果，父请求的其他分项保持原样。页面可重命名、删除会话并导出 Markdown。`/api/sessions/{id}/jobs` 后台启动任务，`/api/jobs/{id}` 查询进度，`/api/jobs/{id}/stop` 请求停止；等待中的模型调用在返回后检查停止状态。会话、分项任务、父请求计划和任务进度由 SQLite 保存。

宽泛的“投放效果”问题不会继承上一轮策略复盘，也不会接受模型猜出的策略、渠道或时间窗；缺少关键条件时展示澄清卡。明确提到腾讯和抖音的宽泛问题可选择一个渠道或“两者分别看”；选择后者时，系统在同一任务中分别计算并复核两渠道，只交付一份综合报告，不会生成两条新用户提问。澄清卡展示实际目标期、对比期及 T7 成熟度提示；等待区展示已确认范围和阶段状态。旧版误判成策略复盘的历史结果在页面上标记为失效，不会覆盖原始记录。

“投放效果不好”现在默认保留为综合诊断目标，只对缺失的时间和渠道澄清；不强迫用户先从成本、消耗和质量中单选。系统先比较两渠道的规模、CPS、安全过件率和首借金额，再按实际变化选择成本拆解、拿量链路或质量分组检查；每项检查保存触发依据和结果。明确提出单一指标的窄题仍走原分析器。5% 相对变化和 1 pp 安全过件率变化目前只用于决定是否下钻，不是业务异常或投放调整阈值。

常见复合问题增加了问题驱动调查：先识别用户要作出的判断和待核实前提，再按需组合逐日趋势、分组对比、质量与动支链路、媒体口径对账、回传机制、模型影响、数据对账和放量候选初筛。结果页展示实际采用的方法、数字和证据边界。若缺媒体后台、模型 PSI／KS、回传规则覆盖率或真实预算余量，系统只报告已有数据可判定的部分及补数动作；不会用 CPS 分解代替原问题。“昨天”超出数据最新日期时会明确提示缺失日期。对应的 14 道真实问法回归记录见 `evals/`。这些方法仍是有边界的本地模拟能力，并不等于可以分析任意新数据源或证明业务因果。

当前仍是本地模拟数据 MVP：覆盖四类 Showcase 主路径、部分推荐追问，以及“投放效果”类综合诊断。综合诊断可根据首轮数据选择后续检查，但候选方法仍限于已有成本、规模、质量工具；尚不能处理任意开放问题。多问题由分隔符识别，父计划暂为分项并发；跨题查询复用或跨题依赖调度尚未完成。临时 SQLite 仅映射本地模拟 CSV，未接入数仓 MCP；分析器目前仍直接读取相同 CSV 计算，不以 SQL 查询结果作为唯一输入。逐素材贡献、真实媒体竞得日志、成熟 Vintage 与设备级随机实验所需数据目前不存在。LangGraph 原生 checkpoint/interrupt、自动 Context Compaction、完整回归评测和生产级权限隔离也尚未完成。

## 一、这套环境是干什么的

同一套业务世界、同一批数据、同一份知识库，支持 **4 个不同类型的分析题**（成本 / 规模 / 质量 / 策略复盘）。

设计目标是让竞品回答的不是“数据是多少”，而是：

> **在给定观察窗口中，数据如何变化？证据能定位到哪一步？该找谁核查或处理？**

具体考察四项能力：

| # | 能力 | 体现方式 |
|---|---|---|
| 1 | **量化分解** | 用恒等式拆解结果指标，给出各因子的贡献度 |
| 2 | **反事实 / 对照** | 做剔除测算或双重差分，剥离大盘趋势 |
| 3 | **机制理解** | 用 `eCPM = Bid × pCTR × pCVR` 之类的机制公式框定搜索空间，而不是逐个维度遍历 |
| 4 | **诚实边界** | 明确区分"可判定"与"只能列可能"，并给出证伪路径 |

## 五、表之间如何关联

```text
                    ads_rta_media_daily   （媒体日级 · 大盘，120 行）
                              │  date + media
        ┌─────────────┬───────┴────────┬──────────────┐
        ▼             ▼                ▼              ▼
 segment_daily   funnel_daily    quality_daily   delivery_daily
 （RTA 策略/      （客群分层）      （RTA 策略/      （RTA 策略/
   版位/账号/                      账号）         账号）
   客群分层）
        │
        ▼
 strategy_experiment （客群分层中 3W2Q / 3W3Q 两个子集）

 creative_daily （抖音素材，按 date 汇总 = 抖音媒体日）
 change_log     （按 变更日期 = date 关联到所有表）
```

### 关联键速查

| 关联 | 键 |
|---|---|
| 全部表 ↔ 全部表 | `date` |
| 渠道相关表 | `media` |
| 细分表之间 | `media` + `segment_type` + `segment_name` |
| `funnel_daily` ↔ `segment_daily` | `media` + `date` + `客群分层` = `segment_name`（当 `segment_type='客群分层'`） |
| `strategy_experiment` ↔ `segment_daily` | `media` + `date` + `分组`（实验组 = 3W2Q，对照组 = 3W3Q） |
| `creative_daily` ↔ `media_daily` | 按 `date` 汇总素材表的花费/曝光/点击 = 抖音媒体日 |
| `adgroup_hourly` ↔ `media_daily` | 按 `date + media` 汇总花费/曝光/点击/首登数 = 媒体日表；T0/T3/T7 转化因归因 cohort 与首登 cohort 不同而不能直接对账，广告组不与旧细分维度直接关联 |
| `change_log` ↔ 全部表 | `变更日期` = `date` |

### ⭐ 三条关键约定

| # | 约定 |
|---|---|
| 1 | **每个 `segment_type` 是同一大盘的独立切分，之和精确等于大盘**。❌ 不要跨 `segment_type` 相加 |
| 2 | **原日级表的转化类字段为首登 cohort 的 T0–T7 累计终值**；小时表 T0/T3/T7 为归因触达 cohort 的累计终值；花费、曝光、点击按实际发生日/小时记录 |
| 3 | **`转化数` = `动支数`**（本环境定义），因此**计费比 = `花费 ÷ 转化数 ÷ 基础出价`** |

## 六、如何重新生成

在当前项目根目录运行：

```bash
# 会覆盖原有 8 张日级 CSV；需要重建数据时再执行
python3 scripts/generate_sim_data.py
# 依赖媒体日表，重新生成第 9 张小时广告组 CSV
python3 scripts/generate_intraday_data.py
```

**依赖**：仅需 Python 3 标准库（`csv` / `math` / `hashlib` / `datetime`），**无第三方依赖**。

**确定性保证**：所有"随机"波动均由 `hashlib.md5(seed|key)` 派生，同一天同一字段的结果稳定，因此**可以放心重新生成并复现全部结论**。

## 七、如何重跑校验

在当前项目根目录运行；前两条不会改写现有 CSV：

```bash
python3 scripts/scan_public_leakage.py     # 公开材料泄露扫描
python3 scripts/inspect_metrics.py         # 关键窗口指标对比（标准输出）
python3 scripts/validate_intraday_data.py  # 小时表主键、行数分布、日级对账
```

`validate_sim_data.py` 会将四题关键计算和检查结果写入非公开目录。当前工作区没有该目录；确需运行时，先创建仅供内部使用的输出目录，再执行：

```bash
mkdir -p 99_GroundTruth_仅供验证
python3 scripts/validate_sim_data.py
```

此脚本能复算数据，不会补齐缺失的题面、评分参考或独立审计材料。重新生成 CSV 的命令见上一节。

**退出码**：以上校验脚本 0 = 通过，非 0 = 失败。

### 7.1 一致性校验的通过标准

| 编号 | 检查项 | 通过标准 |
|---|---|---|
| C1 | 细分汇总之和 = 渠道大盘 | 每个 `segment_type`、每个字段、每一天，偏差 < 0.5% |
| C2 | 指标公式可复算 | 10 个恒等式，相对误差 < 1e-6 |
| C3 | 漏斗单调 + 安全授信 ≤ 授信 | 全部行满足 |
| C4 | 比率字段在合理区间 | 0 违例 |
| C5 | 事件与指标变化的时间一致性 | 4 项子检查 |
| C6 | 4 个 Showcase 的结论可复算 | 输出全部关键计算结果 |

## 九、已知限制

### 9.1 数据层面的限制

| # | 限制 | 影响 |
|---|---|---|
| 1 | **小时表的投放量由日表拆分，转化为归因触达 cohort 的离线 T0/T3/T7 终值**；没有分钟级序列或盘中未成熟快照 | 可练习广告组小时分布和事后 cohort 复盘，但不能据此还原真实故障时点，或把 T0/T3/T7 当成盘中实时授信、动支 |
| 2 | **无用户级明细** | 无法抽样核验、无法做分群画像分析 |
| 3 | **无模型侧数据**（PSI / KS / 分档分布） | 无法验证"模型退化"这条归因路径 |
| 4 | **素材数据只有抖音** | 腾讯侧无法做素材分析 |
| 5 | **客群分层只有 5 个具名组合**，非完整 W1–W5 × Q1–Q5 | 无法下钻到具体 W/Q 格子 |
| 6 | **`Vintage30逾期率` 为构造值**，仅与安全交易占比反向单调相关 | 不具备真实贷后时间结构，不应据其推导具体贷后结论 |
| 7 | **`完播率3秒` 为派生构造值** | 不应据其推导素材创意质量结论 |
| 8 | **`pCTR` / `pCVR` 为媒体侧预估值**，按实际比率加扰动构造 | 不应据此推导媒体模型的具体参数 |
| 9 | **只有 3 类素材形式**（口播 / 剧情 / 图文），无真人 vs AIGC 等维度 | 无法考察素材类型对比 |

### 9.2 业务设定层面的限制

| # | 限制 | 说明 |
|---|---|---|
| 1 | **不含"代理"角色** | 真实业务的执行链路上存在代理，本环境简化为业务方直控 |
| 2 | **渠道级 CPS 基线为构造值** | 源资料中不存在渠道级 CPS 的真实值 |
| 3 | **阈值体系为构造值**，但保留了"跨渠道失准"的真实特征 | 见 03 文档 4.2 节 |
| 4 | **策略实验为客群级对照**，非设备 ID 分桶实验 | 表结构上只有分组列，没有分桶 ID |
| 5 | **无外部大盘数据** | 无法分离"行业竞价环境"因素 |
| 6 | **数据噪声整体偏低** | 各子组的同步性高于真实业务；本环境更接近"可比的考试题"而非"高噪声的真实环境"（详见 9.4） |

### 9.3 ⚠️ 指标时间的口径声明（重要，关系到能否回答"今天"）

| # | 声明 |
|---|---|
| 1 | **所有转化类指标（首登 / 申完 / 授信 / 安全授信 / 发起 / 动支 / 首借金额）均按 T0–T7 累计终值模拟**，即：某一天的行代表“以该日为首登日、并在其**后 7 天内**完成的转化”。 |
| 2 | **这与真实世界的"当天可获得的实时数据"不等价。** 真实业务中，2026-09-26 当天下班时，09-26 的首借金额只回填了一小部分，不可能拿到 T0–T7 的完整值。 |
| 3 | 因此，本环境的每日数据应理解为**预先构造的 cohort T7 终值**，而不是“当天的实时快照”或当天已成熟的数据。 |
| 4 | **本 Benchmark 的 4 个 Query 是离线终值分析，不是观察日的实时诊断。** “近 7 天 / 前 7 天 / 近 30 天”是数据文件中的回顾窗口，不表示这些 cohort 在 2026-09-26 已完成成熟期。以该日为真实观察日时，只有首登日不晚于 2026-09-19 的 T7 cohort 完成观察期。 |
| 5 | 若未来要做"当天实时判断"类题目，需要另建一套**未成熟口径**的数据（各转化节点按实际发生日回填），不能复用本环境。 |

### 9.4 数据构造性质声明

| # | 声明 |
|---|---|
| 1 | **这是构造数据，不是真实业务数据。** 其中的业务波动与指标变化是按设计生成的，而非自然发生的。 |
| 2 | **本环境为模拟构造数据，部分统计关系具有构造属性。** 分析时应基于实际证据判断，**不应仅凭相关性或表面趋势建立因果结论**。 |
| 3 | **数据噪声低于真实业务**：日间随机波动偏小。**不应把"现实业务的经验直觉"直接套用到本环境上。** |
| 4 | **设计初衷**：作为 Benchmark，优先保证"不同竞品面对完全相同的世界、结论可横向比较"。**牺牲了部分真实性以换取可比性。** |

## 十、一句话总结

> **这套环境提供的不是"正确答案"，而是"一个可以用数据把答案推出来的世界"。**
> 原设计把四类问题放在同一时间轴上，供分析者比较成本、规模、质量和策略变化。
> 当前工作区可用知识库和模拟数据练习分析；若要开展完整竞品评测，须补齐题面与内部评分材料，并将“时间关联”与“已验证的因果”分开评价。
